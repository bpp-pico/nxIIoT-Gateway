# nxIIoT Gateway — industrial IoT edge gateway with a real MQTT sink

Modbus RTU/TCP acquisition → local SQLite store & forward → MQTT delivery to a real Internal Server, running live on a Raspberry Pi. For the deep architecture rationale and per-phase history see [HANDOFF.md](HANDOFF.md) and [industrial_iot_gateway_handoff_dev_plan.md](industrial_iot_gateway_handoff_dev_plan.md); for the Pi deployment blow-by-blow see [DEPLOY_PLAN.md](DEPLOY_PLAN.md).

## Architecture

- **`gateway/`** (Go) — the edge device binary. Modbus config is split into `connection` (the physical link — protocol/interface-or-ip+port/baud/parity/timeout/retry/**next_device_delay_ms**, `internal/connection`) and `device` (a slave ID + its data points, referencing one `connection_id`, `internal/device`) — several devices can share one physical RTU bus (real multi-drop). `internal/acquisition` polls one goroutine **per enabled connection**, not per device: `Poller.runConnection` owns a single `modbus.Client` for the connection's lifetime and calls `SetUnitID` before each sibling device's own reads, serialized by construction. As of the 2026-09-02 polling redesign, there's no ticker/interval scheme any more — devices are scanned continuously, round-robin, paced only by `next_device_delay_ms` between devices; each device's datapoints are batched into as few Modbus block reads as possible (`internal/acquisition/blockplan.go`) instead of one request per datapoint. `internal/queue` persists every reading to SQLite (WAL) as `data_queue` with an atomic per-gateway `sequence_id`; `internal/forwarder` ticks on `forwarder.poll_interval_ms` and dispatches batches through an `Adapter` interface — `MQTTAdapter` in production (QoS 1 + application-level ack over a dedicated ack topic), `HTTPAdapter` for dev/test. Acquisition and forwarding never block each other (Rule 1) — a dead broker just grows the local queue.
- **`web/`** (React + TS + Vite) — the gateway's own local admin UI: Dashboard, Devices, Store & Forward, Time, Diagnostics, Logs, Config. Talks to the gateway's REST API only.
- **`internal-server/`** (Go, separate module) — the real downstream consumer. Subscribes `gateway/+/data` on the MQTT broker, dedupes into Postgres on `gateway_id`+`sequence_id`, acks back on `gateway/{id}/ack`, and serves its own dashboard (`/dashboard`) + JSON API (`/health`, `/latest`, `/readings`, `/stats`). Runs via `docker compose up -d` (project name `nxiiot-internal-server`) on `vd-ct-app-srv` (`192.168.99.200`, user `vendor-app`) — a vendor-managed always-on Ubuntu server, not the Windows dev laptop it started on.
- **Deployment target**: a real Raspberry Pi (`NXGE-RPI`, Debian 13 trixie, aarch64), native/systemd (not Docker — needed for `/dev/rtc0` and real `nmcli`), reachable over Tailscale. `gateway/deploy/nxiiot-gateway.service` (`Restart=always`) is the reference unit.
- **Real MQTT broker**: `mqtt.nxge.co:1883` (plain TCP, no auth/TLS yet) — both the Pi's gateway and `internal-server/` point at this, not the dev-only `mosquitto` service in the repo root's `docker-compose.yml`.

- **Fixed a real MQTT reconnect-watchdog bug that made a ~9h outage far worse than it needed to be** (2026-09-02, same incident as above) — while investigating the network outage, live Pi logs showed `RunReconnectWatchdog` (shipped 2026-08-27, see Session 7 below) firing every `WatchdogInterval` (1 min) and failing every single time from at least 08:44 to 17:47 local (~9h), always with the same error: `"status can only transition to connecting from disconnected"`. Traced to paho.mqtt.golang's actual source (`status.go`'s `errStatusMustBeDisconnected`, vendored at v1.5.1): this error means paho's own `AutoReconnect`/`ConnectRetry` goroutine was already mid-attempt (status `connecting`/`reconnecting`) — i.e. paho was actively, correctly retrying on its own the whole time, and the watchdog's old code (1) misclassified every one of those as a failure and (2) made things actively worse by calling `client.Disconnect(250)` unconditionally right before its own `Connect()` call, tearing down paho's legitimate in-flight attempt once a minute for 9 hours straight. Root cause: the original Aug 27 fix was designed around a *different* failure mode (paho silently stalled, status genuinely `disconnected`, zero retry activity) and never accounted for the much more common case of "paho is still actively retrying but the network is genuinely down for a while." Fixed in `gateway/internal/forwarder/mqttadapter.go`'s `checkAndForceReconnect`: removed the preemptive `Disconnect()` call, and added `isPahoAlreadyReconnectingErr` to detect this specific paho error and log it as informational ("watchdog took no action") instead of an error requiring escalation. New unit test (`mqttadapter_internal_test.go`) locks in the exact string match against paho's real error text so a future paho version bump that changes the wording fails loudly instead of silently reintroducing this. Built/tested clean on both the dev machine and natively on the Pi; live-verified post-deploy: `mqtt connected` immediately on restart, zero reconnect-error log lines since, `retry_count` reset to 0, and the backlog drain rate visibly improved (562,679 → 455,922 pending in the following few hours, versus barely moving while the old watchdog was fighting paho). - **SD-card I/O bottleneck (from the polling redesign below) — real root cause found and fixed, live-verified (2026-09-02, follow-up session).** Re-checked live before touching anything: `last_poll_duration_ms` was still 10.2s/10.4s (down from 15.7s/40s but far from the 678ms/1014ms baseline), `gateway.db` had grown to 772MB, 298,919 rows still pending. Investigated further instead of accepting the original three candidate directions (reduce/archive backlog, move db off SD card, acquisition-loop backoff) at face value: `GET /api/diagnostics` showed `avg_response_time_ms: 37.4ms` with zero timeouts/CRC errors — real Modbus hardware was fast and healthy the whole time, ruling out RTU bus contention. `journalctl` showed the retention sweeper has never once deleted a row (nothing is 30 days old yet) and disk usage (27%) never crosses the 95% storage-pressure eviction threshold, ruling out a giant-DELETE-holds-the-write-lock theory too. The actual cause: [gateway/internal/storage/storage.go](gateway/internal/storage/storage.go)'s `Open()` had `db.SetMaxOpenConns(1)` — every DB operation in the whole gateway (acquisition inserts, forwarder fetch/mark, retention/storage sweeps, *and every Web UI/API read* like `/api/store-forward/status`, which the Dashboard polls every ~5s) was forced through one single serialized SQLite connection, even though WAL mode (already configured) is specifically designed to let readers run concurrently with the one writer SQLite itself enforces. A slow read query on a 772MB table blocked the acquisition goroutine's own time-critical insert behind it in the same queue — that produced the multi-second `last_poll_duration_ms` spikes, not the polling loop being "too continuous." Fixed by raising `SetMaxOpenConns` to 4 (`busy_timeout(5000)` handles the rare concurrent-writer collision); also added `cycleYieldDelay` (20ms, `internal/acquisition/poller.go`) — a small breathing gap once per full round-robin pass over all devices, on top of the existing per-device `next_device_delay_ms` — kept as defense-in-depth per explicit user direction alongside the connection-pool fix. New test `TestRunConnectionYieldsOnceAfterEachFullPass`; existing poller tests updated to zero out the new delay so their cycle-count timing assertions still hold.

## Data Contracts

Interfaces between components — flag before changing any of these, since gateway, `internal-server/`, and (for the MQTT ones) the broker's other future consumers all depend on them matching exactly.

- **MQTT data topic** (gateway → broker): `gateway/{gateway_id}/data`, QoS 1, JSON:
  `{ "batch_id": string, "entries": [{ "gateway_id": string, "sequence_id": int64, "device_id": int64, "datapoint_id": int64, "value": float64|null, "quality": "GOOD"|"CRC_ERROR"|"DEVICE_OFFLINE"|"INVALID"|"TIMEOUT", "event_timestamp": RFC3339, "priority": string }] }`
  (`gateway/internal/forwarder/wire.go`'s `WireEntry`, mirrored in `internal-server/consumer.go`'s `wireEntry`.)
- **MQTT ack topic** (consumer → gateway): `gateway/{gateway_id}/ack`, QoS 1, JSON: `{ "batch_id": string, "error": string (optional) }`. Any consumer must derive this from the data topic it received (`strings.TrimSuffix(topic, "/data") + "/ack"`), not hardcode a gateway ID — `internal-server/` subscribes with a `gateway/+/data` wildcard specifically so this works across a fleet.
- **Gateway REST API → Web UI**: connections (`GET/POST/PUT/DELETE /api/connections`), devices (`GET/POST/PUT/DELETE /api/devices`), and datapoints (`GET/POST/PUT/DELETE /api/datapoints`). A device carries only `connection_id`/`slave_id`/`polling_interval_ms`/`enabled` — protocol/interface/baud/etc moved to the connection it references (Session 8 split). Devices and datapoints both carry their own `polling_interval_ms` field — they are independent gates (see MEMORY.md's entry on this), not a device-level override of a datapoint default. `DELETE /api/connections/{id}` returns `409` while any device still references it. Config export/import (`GET/POST /api/config/export|import`) carries a top-level `connections` array restored before `devices` — this is a breaking change to the exported JSON shape versus pre-Session-8 exports.
- **`internal-server/` JSON API**: `GET /readings` and `GET /latest` return the same row shape (`gateway_id`, `sequence_id`, `device_id`, `datapoint_id`, `value`, `quality`, `event_timestamp`, `priority`, `received_at`) — `/latest` is one row per `(gateway_id, device_id, datapoint_id)` via `DISTINCT ON`, `/readings` is the full filtered history. `/readings` also accepts `since` (RFC3339, filters on `received_at >=`) — added for the dashboard's Trend chart's time-range picker; when `since` is given without an explicit `limit` the default cap rises from 100 to 5000 (both hard-capped at 5000).
